# Localization (String Catalog) — agent notes

Hermex ships four String Catalogs and one classic InfoPlist localization:

- `HermesMobile/Resources/Localizable.xcstrings` — shared UI copy, bundled in the
  main app, share extension, Live Activity widget and Notification Service
  Extension (which reads four keys: the content-free `New activity` fallback and
  the banner titles `%@ · Approval needed`, `%@ · Question` and
  `%@ · Turn failed`).
- `HermesMobile/Resources/AppShortcuts.xcstrings` — the eleven App Shortcut
  invocation phrases, bundled in the main app only.
- `HermesMobile/Resources/Auxiliary.xcstrings` — five app/widget strings that
  previously bypassed extraction, bundled in the main app and Live Activity
  widget.
- `HermesShareExtension/Resources/ShareExtension.xcstrings` — five
  extension-specific status and error messages, bundled in the share extension.
- `HermesMobile/Resources/ca.lproj/InfoPlist.strings` — the seven permission
  prompt descriptions, loaded by iOS from the main app bundle.

The auxiliary and share catalogs currently contain English and Catalan only.
Other shipped languages fall back to their English source there, matching the
pre-localization behavior instead of changing existing translations.

## Adding a language

1. Add the code to `knownRegions` in `HermesMobile.xcodeproj/project.pbxproj`.
2. Add the code to `shippedLanguages` in the localization test guard.
3. Add every key's translation to `Localizable.xcstrings` with
   `"state" : "needs_review"`.
4. Add the language to all eleven phrases in `AppShortcuts.xcstrings`. Keep the
   `${applicationName}` and `${profile}` placeholders — the system substitutes the
   app name and the intent supplies the profile.
5. Add the language to `Auxiliary.xcstrings` and `ShareExtension.xcstrings` when
   shipping Catalan.
6. Add `InfoPlist.strings` in the locale's `.lproj` directory for permission
   descriptions.

`Localizable` and `AppShortcuts` require complete values for every shipped
language. The auxiliary and extension catalogs require an English source and a
complete Catalan value in addition to their existing fallback behavior.
`testShippedLanguageTranslationsHaveNoEmptyValues` catches empty `Localizable`
values, while the focused tests cover plural branches, auxiliary/share catalogs,
and permission descriptions.

Missing keys are guarded separately. This repo does **not** write extracted
strings back into the catalog on build, so PR CI runs
`ci/check_string_catalog.py` after its Debug build: it reads the `.stringsdata`
files the compiler emits for the app, Live Activity widget, and Notification
Service Extension, plus the share extension, and fails, naming each key, file,
and target when a `Localizable` key is absent from `Localizable.xcstrings`.
Stale catalog keys and
`shouldTranslate: false` entries never fail it. Run it locally against any
finished build of the `HermesMobile` scheme:

```zsh
python3 ci/check_string_catalog.py --derived-data <DerivedData path>
```

Fix a miss by adding the key with every shipped translation (below). CI builds
Debug, so copy compiled only under `#if DEBUG` is extracted too: keep it out of
the catalog with `Text(verbatim:)` or a plain `String` instead of a
`LocalizedStringKey`.

Tests are pinned to `en` in the scheme's TestAction. Do not change that.

## Editing the catalog

`Localizable.xcstrings` mixes compact grouped entries and expanded entries.
There is no verified canonical full-file serializer.

1. Parse the existing JSON before editing.
2. Make a targeted edit preserving untouched bytes, key order, and formatting.
3. Parse the result and compare semantic subtrees. Only the intended keys and
   languages may change; check placeholder parity with the source strings.
4. Inspect the text diff for unrelated formatting churn. A full-file formatter
   needs a byte-for-byte round-trip check against the current catalog before use.

## Plurals

Derive and verify plural categories in Xcode for each locale being edited.
Language-family shortcuts are not a source of truth. Check existing categories
against that locale's requirements rather than copying them into new entries.

## Locale-aware casing

`String.uppercased()` is locale-insensitive and wrong for Turkish
(`i` → `I` instead of dotted `İ`). Use `Text(x).textCase(.uppercase)` instead,
matching `InsightsView`. When adding any special-casing language, grep **all**
`Text(...uppercased())` sites — without head-truncating the results.

## RTL

RTL is language-driven only: it applies to RTL languages, and LTR layout stays
byte-identical. The app already uses semantic `.leading` / `.trailing`, so the
RTL work was a small `RTLLayout` helper plus `chevron.right` → `chevron.forward`
swaps. There is deliberately **no** app-wide RTL toggle.

Test RTL without an RTL language in the bundle, via the pseudolanguage:

```zsh
xcrun simctl launch <udid> com.uzairansar.hermesmobile \
  -AppleTextDirection YES -NSForceRightToLeftWritingDirection YES
```

Relaunch without the flags to return to normal LTR. To launch in a real
language: `-AppleLanguages '(pl)' -AppleLocale pl_PL` (terminate first so the
argument re-applies).

## Batching many languages

Translation batches worked well as: glossary first (brand terms verbatim +
register — German uses informal *du*) → chunk the English source ~50 keys per
sub-agent → translate in parallel → validate placeholder parity against the
English positional specifiers (`%1$@`, `%2$@`) → deterministic merge asserting
total key coverage.

Because every batch edits the single shared `Localizable.xcstrings`, parallel
branches always conflict. **Stack each batch's branch on the previous one** and
`git rebase --onto master <prev-tip>` after the earlier one squash-merges.
