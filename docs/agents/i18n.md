# Localization (String Catalog) — agent notes

Hermex ships one String Catalog, `HermesMobile/Resources/Localizable.xcstrings`,
included in the app, widget, and share-extension targets. Every user-facing
literal is already externalized (`String(localized:)` / `LocalizedStringKey`), so
adding a language is normally **translation-only** — no Swift edits.

This file holds the non-obvious mechanics. It is not a tutorial.

## Adding a language

1. Add the code to `knownRegions` in `HermesMobile.xcodeproj/project.pbxproj`.
2. Add the code to `shippedLanguages` in the localization test guard.
3. Add every key's translation to `Localizable.xcstrings` with
   `"state" : "needs_review"`.

`LocalizationCatalogTests.testShippedLanguageTranslationsHaveNoEmptyValues`
loops over `shippedLanguages` and fails on any empty value, so a partial batch
is a red build. Note the inverse: keys **absent** from the catalog do not fail
the guard, and this repo does **not** auto-extract strings on build — a new UI
string that never reaches the catalog is silently English-only forever.

Tests are pinned to `en` in the scheme's TestAction. Do not change that.

## Catalog file format is Xcode-exact

`Localizable.xcstrings` must round-trip byte-identically or every unrelated
language churns in the diff. Xcode's serialization is:

```python
json.dumps(d, ensure_ascii=False, indent=2, sort_keys=True, separators=(',', ' : ')) + "\n"
```

Two traps:

- **Do not rewrite the whole file** with a naive `json.dump` — it reorders keys.
  Entries are in grouped-append order, not sorted. For a small batch of new
  keys, append serialized entries (2-space indent, `" : "` separators) directly
  before the `\n  },\n  "version" : "1.0"\n}` tail anchor.
- **Verify with a parsed-subtree diff**, never the raw line diff. The raw diff
  churns from key reordering even when nothing semantically changed. Assert that
  no pre-existing language's parsed subtree changed.

## Plural categories differ per language

The catalog's plural keys need the correct CLDR category set. Author these by
hand — do not delegate them:

| Languages | Categories |
|---|---|
| Romance, German, Dutch, Turkish | `one`, `other` |
| Polish, Russian | `one`, `few`, `many`, `other` |
| Japanese, Chinese, Korean | `other` only |
| Arabic | `zero`, `one`, `two`, `few`, `many`, `other` |
| Hebrew | `one`, `two`, `many`, `other` |
| Urdu | `one`, `other` |

## Locale-aware casing

`String.uppercased()` is locale-insensitive and wrong for Turkish
(`i` → `I` instead of dotted `İ`). Use `Text(x).textCase(.uppercase)` instead,
matching `InsightsView`. When adding any special-casing language, grep **all**
`Text(...uppercased())` sites — without head-truncating the results.

## RTL

RTL is language-driven only: it applies to RTL languages, and LTR layout stays
byte-identical. The app already uses semantic `.leading` / `.trailing`, so the
RTL work was a small `RTLLayout` helper plus `chevron.right` → `chevron.forward`
swaps. There is deliberately **no** app-wide RTL toggle.

Test RTL without an RTL language in the bundle, via the pseudolanguage:

```zsh
xcrun simctl launch <udid> com.uzairansar.hermesmobile \
  -AppleTextDirection YES -NSForceRightToLeftWritingDirection YES
```

Relaunch without the flags to return to normal LTR. To launch in a real
language: `-AppleLanguages '(pl)' -AppleLocale pl_PL` (terminate first so the
argument re-applies).

## Batching many languages

Translation batches worked well as: glossary first (brand terms verbatim +
register — German uses informal *du*) → chunk the English source ~50 keys per
sub-agent → translate in parallel → validate placeholder parity against the
English positional specifiers (`%1$@`, `%2$@`) → deterministic merge asserting
total key coverage.

Because every batch edits the single shared `Localizable.xcstrings`, parallel
branches always conflict. **Stack each batch's branch on the previous one** and
`git rebase --onto master <prev-tip>` after the earlier one squash-merges.
